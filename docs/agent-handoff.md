# Agent handoff

Shared scratchpad for all agents (Claude, Codex, Gemini). Created on 2026-11-21 at William's request.

## How to use this file

- Each open entry is its own file in [handoff/](handoff/) (T77), listed under "Open exchanges" below. Read this file, then the entries you're picking up; preserve the other agent's wording, re-read before writing, and append a dated, signed response at the end of the entry's file. File changes do not automatically notify other agents.
- Keep entries short: a stable ID, author, date, status (`open`, `queued (after H0NN)`, `answered`, `resolved`), relevant references, and a concrete request or finding.
- This file coordinates work; it does not approve new behaviour or override William's decisions. Move lasting specifications to the design documents and approved decisions to the decision log, keeping a short resolution here linking to them.
- A new entry is a new file, `docs/handoff/H-new-N-short-slug.md` (copy the template at the bottom; N = 1, 2 ... on your branch); the integrator numbers it at merge with `tools/NUMBER_A_NEW_ID.py` (T74). The open list and the last 10 archived lines are generated by `python3 tools/handoff.py tidy` (run by the pre-commit hook and at merge; don't edit them by hand). If an entry was written inline by habit, `python3 tools/handoff.py split` moves it to its own file.
- When an entry is resolved, `python3 tools/ARCHIVE_A_FINISHED_JOB.py H0NN` moves it whole to [handoff-archive.md](handoff-archive.md) and tidies "Archived" below to the last 10 entries. Either agent may archive a resolved entry; read the archive only when you need an entry's history.
- For job rules (claiming, `Touches`, responses, `Result:`, `Follow-up:`, `For the integrator:`, and submitting), see [BOARD.md](../BOARD.md).

## Entry template

Save as `docs/handoff/H-new-N-short-slug.md`; the number is given at merge.

### H-new-N — Short subject

Author: Claude or Codex | Date: YYYY-MM-DD | Status: open | For: who should act on it

References: decision IDs, files, commits, or tests.

Touches: the files this job expects to change (P11).

Finding or request: ... Each rule says what it's for ("RELEASE_DEG never below INFER_DEG, so an axis can't let
go before it sticks"), so the worker can tell when the letter defeats it (P44).

What can fail (a job touching saving, reloading or the worker link, P42): each step that can fail (a file
missing or unreadable, the worker gone, a reply late or out of order, a dialog open while replies arrive), what
should happen, and the named check that proves it. The worker may add cases, not drop any.

Response — Author, YYYY-MM-DD: ... (a `Changed from the brief:` line per departure, P44)

Resolution: ...
